# Plan: read .rgbv videos and check the 9 clips against manifest.json

## Already checked on the real files (0.4.6-17)
Folder: `workspace/unpacked/<v>/base/assets/Video/`: 9 clips, each with a `.mp4` and a `.rgbv`, plus `manifest.json` (version 35).

**.rgbv layout (true for all 9 files, no bytes left over):**
| Offset | Size | Field |
|---|---|---|
| 0 | u32 LE | fps (15 or 30) |
| 4 | u32 LE | frame count (48–180) |
| 8 | repeated | per frame: u32 LE byte size, then one whole JPEG (starts `FFD8`, ends `FFD9`) |

The JPEGs were written by ffmpeg (`Lavc62.28.100`). Frame count equals the number of JPEGs found in each file. Nothing is unknown, so the docs will mark every field as verified. Width and height come from each JPEG's SOF header, not from the .rgbv header.

**Manifest vs files: every clip is different.**
- None of the 9 `.mp4` files match the manifest's `bytes` or `sha256` (e.g. summon_bronze is 7,376,088 bytes; the manifest says 2,294,417).
- The manifest says 30 fps for every clip, but 4 `.rgbv` files are 15 fps. summon_bronze has 180 frames at 30 fps (6.0 s), but the manifest says 4.2 s.
- So the manifest is out of date compared with the shipped videos. The stage reports this as a finding and still finishes successfully. It doesn't fail, because if it did, `zk video`, and later `zk update`, would always fail on this build.

**Generator script:** `Tools/v20_video/render_procedural.py` isn't in the APK, and you said you don't have it. The decoded files are the only source, and the docs say so.

## What I will build
1. **`src/zk/formats/rgbv.py`** (pure, stdlib): `parse(data: bytes) -> Rgbv`, where `Rgbv` holds fps, frame_count and `frames: tuple[bytes, ...]`. It raises `ValueError` on a short header, a size that runs past the end, a frame without SOI/EOI, a count that doesn't match, or leftover bytes. It also has `jpeg_size(frame) -> (w, h)`, which reads the SOF0/SOF2 marker.
2. **`src/zk/formats/mp4.py`** (pure, stdlib): walks the boxes `moov/mvhd` (duration), `trak/tkhd` (width, height), and `mdia/mdhd` + `stbl/stts` of the video track (fps). It only reads boxes, so it never decodes video.
3. **`src/zk/formats/video_manifest.py`**: reads manifest.json into frozen dataclasses and checks that every required key is there with the right type.
4. **Port `video_encoder`** (`src/zk/ports/video_encoder.py`): `encode(frames_dir, fps, out) -> dict`, plus its contract (the output file exists and isn't empty). Register it in `PORTS`, and add it to `tests/test_contracts.py`.
5. **`src/zk/adapters/ffmpeg.py`**: finds ffmpeg only with `shutil.which("ffmpeg")`, or with an optional `[options.video_encoder] path`. It never downloads anything. If ffmpeg is missing, it raises a clear error.
6. **`src/zk/stages/video.py`**: `zk video [--encode] [--force]`, added to `STAGE_MODULES` after `assets`.
   - Finds the Video folder from the `unpack` record in the manifest.
   - Goes one clip at a time and writes `assets/<v>/video/<clip>/frame_0000.jpg …`, the raw JPEG bytes unchanged. Clips that are already exported (index.json) are skipped unless `--force` is used.
   - For each clip, compares the manifest against the `.mp4` (bytes, sha256, duration, fps, width, height) and against the `.rgbv` (fps, frames/fps as duration, JPEG size). It also lists clips that exist on only one side.
   - Writes `assets/<v>/video/report.json` with each field showing expected, actual and ok. It returns a summary to the manifest (`clips`, `frames`, `mismatches`). A mismatch is reported but doesn't change the exit code. Bad .rgbv bytes or a missing folder do fail the stage.
   - `--encode` is the only flag that calls the `video_encoder` port. Without ffmpeg, it fails with a "install ffmpeg or drop --encode" message.
7. **Config/docs:** in `zk.toml`, `video_encoder = "ffmpeg"`. New files: `docs/formats/rgbv.md` (layout table, all fields verified, no generator script), `docs/stages/video.md` (inputs, outputs, report, real-run results including the out-of-date manifest), `docs/ports/video_encoder.md`, and `docs/adr/0007-video-encoder.md`. Also link them from `docs/index.md` and `docs/architecture.md`.

## Risks
- Real files total about 170 MB. The stage reads one clip at a time.
- MP4 timing could use edit lists or a variable frame rate. fps comes from `stts` (sample count / media duration), and duration from `mvhd`. If they differ, that's reported, not hidden.
- ffmpeg isn't on CI. Tests only check the command line it would build, and use a fake encoder.

## How I check it
- `python -m pytest -q`, using made-up bytes only: a good .rgbv with 3 tiny JPEGs, plus each bad case; made-up MP4 boxes; a manifest with a missing key; a stage run with fake clips, including one mismatch and one missing clip; the fake encoder; and the ffmpeg command line.
- `pyright` and `ruff check` pass, and the boundary test stays green.
- A real `zk video` run on 0.4.6-17: 9 clips and 829 frames exported, and the report lists the manifest mismatches above.
